Sibling Ports and Stray Dots

One real bug this session came from a regex that forgot a string made of nothing but dots is still a valid string. A second lead came from not reading a program's own rules before trusting its web form. A third came from a method invented on the spot: take a defense you've already proven real in one codebase, and go check whether the project's own sibling ports actually carried it over.

L24 · Path traversal · 12 min

A regex that blocks slashes, not dots

The whole bug is five steps, and none of them are exotic.

  1. Something gets a name: an artifact, a model, a file. Supplied by whoever calls the API.
  2. The name is checked against a regex. It blocks /, so ../../etc/passwd can't get through as one piece.
  3. The regex still allows a bare . or .. — dots are in the allowed-character list for version strings like v1.2.3, and nobody separately asked "what if the whole string is just dots?"
  4. The name is handed to a path-join function: new File(parent, name), path.join(). These don't care whether name is "foo" or ".." — joining a parent to ".." means "go up one directory", exactly like cd ...
  5. Nobody re-checks the final path. No "is this still inside the folder I meant?" step after the join.
regexCDAP's artifact and version patterns: [\.a-zA-Z0-9_-]+. The string ".." is only dots, and dots are allowed, so it fully matches.
sinkArtifactStore.copyFile(): .append("artifacts").append(name).append(version), then writes the uploaded jar there. No canonicalize-then-contain check anywhere after the join.
libraryChecked the join function itself, not just CDAP's code: Apache Twill's Location.append(child) is literally new File(file, child). No sanitizing, confirmed from its own source.
proofWrote a tiny Java program using that exact join call, fed it CDAP's real regex, and watched it on a real disk: artifact name "..", version "..", file landed one directory above where it should have, next to every other tenant's data.

Trap: reading the join and the regex and concluding "this must be exploitable" without running it. A path-join bug is really three separate facts (the regex allows it, the join doesn't sanitize, and the result lands where you predicted) and each one can be wrong on its own.

Predict

You find a regex [a-zA-Z0-9._-]+ validating a filename, then see it joined into a path with no further check. What's the single most useful next step?

Reading tells you what should happen. Only running the real mechanism — the actual join function, the actual regex, on a real filesystem — tells you what does happen. That's the difference between a hypothesis and a finding.

Produce

Grep a codebase you know for a regex like [\w.-]+ or [a-zA-Z0-9._-]+ validating an id, name, or version. For each hit, write down: where does the validated value get used next? Does it reach a path-join, a file open, a directory create? If yes, is there a containment check after the join, or does the code just trust the regex?

L25 · Filing · 8 min

The form is not the rules

A bounty program's web form has a dropdown of categories. The actual rules live on a different page, and they change.

  1. An automated "out of scope" message from a form is a form's opinion, not a verdict on the bug.
  2. Before accepting it, go read the program's own written rules page — not the dropdown's one-line description.
  3. Rules change on a schedule the form doesn't always reflect. A category can close to a bug class on a specific date and the form can keep offering it anyway.
  4. When a written rule tells you to use a different program, try that one before assuming the bug is simply unwelcome.
try 1Submitted a path-traversal finding under the open-source program. Form: "out of scope".
ruleThat program's own rules page, read in full: as of 1 Oct 2026 it stopped accepting this exact category — "product vulnerabilities" — and named path traversal as its own example of what it no longer takes.
try 2Same rules page named a second program for cloud-related repos. Tried it. Form: "out of scope" again — its matcher wants a live cloud service address, not a bare source-repo link.
try 3The rules index's own stated catch-all ("if you're not sure where to report, use this one") passed, with the warning visible on the submission for a human to re-route.

Trap: treating the first "out of scope" as the final word and dropping a real bug.

Predict

A bug-bounty form rejects your real, verified finding as "out of scope" for the category you picked. What's the right next move?

The form's category list can be stale or just wrong about matching your exact submission shape. The written rules page is the actual source of truth, and it often tells you directly which program to use instead.

L26 · Method · 12 min

Differential port audit: steal from your own proof

The most expensive part of finding a bug is building confidence a hypothesis is worth testing. A defense you've already proven real, in one codebase, gives you that hypothesis for free in every sibling of that codebase.

  1. Multi-language projects usually have one reference implementation that gets fixed first, and sibling ports in other languages that catch up later, if ever.
  2. If you've already execution-verified a specific defense in the reference implementation, that defense is now a checklist item, not a guess, for every sibling port.
  3. Check for the SAME defense by name and mechanism — not "does this port seem secure" in general, which is too vague to act on.
  4. A port that already has the defense is a real result too. It proves the method finds real gaps instead of just flagging everything.
ref.Python's dev server: binds loopback by default, AND checks the real connection's peer address on every request, rejecting anything non-local even if someone widens the bind. Confirmed by reading the actual check.
port AKotlin's port: same safe default, but grepped its whole server module for a peer or origin check — none. Only logging and content-type plugins installed. Documented as the operator's own risk to manage, but the second layer Python has was never built.
port BJava's port: built and ran the actual server. netstat showed it listening on every network interface by default, no flag needed. A live request with a fake Origin header got back "allow any origin". The server's own startup log named two of these as known-insecure defaults, in a log nobody reads at 2am.
port CGo's port: checked the same two things. Defaults to loopback with a clearly written reason in its own help text, and its allow-list of origins is empty until someone explicitly adds to it, with a direct warning against using a wildcard. Clean. The method correctly found nothing here.

Trap: finding a gap in one port and assuming every sibling has the same gap. Port C had the best defenses of all four, better documented than two of the others.

Predict

You've proven a specific defense is real in project X's Python implementation. Project X also ships Go, Java and Kotlin ports. What do you check first in each?

A vague "feels secure" check doesn't transfer your proof from the reference implementation. Checking for the specific, named mechanism does — and ports frequently do NOT copy each other, which is exactly why this method finds real gaps.

Produce

Pick any project you know that ships more than one language implementation of the same server or tool. Name one specific, checkable defense you can verify exists (or doesn't) in each port — not "is it secure", but a named mechanism: a default bind address, an origin check, a permission gate. Write what you'd grep for in each language.
