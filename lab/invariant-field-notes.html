Invariant Field Notes

One pre-registered sweep of MONAI flagged about a dozen things. Three were real bugs. The rest were the harness, randomness by design, or issues already filed. Then one signed-off commit closed a pull request for good, and 21 red CI jobs turned out to be one broken runner.

L22 · ML systems · 10 min

Three invariants that found three bugs

Every check compares against an independent reference: the batch-of-one result, the fp32 result, the eager result. Never just "old version versus new version".

  1. Batch independence. A sample's result must not change when its batchmates change. Score it alone, then next to something very different.
  2. Half precision. Autocast and .half() are different. Test the whole-model cast, and check fp32 activation sizes before calling an fp16 overflow a bug.
  3. Lazy versus eager. Compare metadata (affine, spacing, origin), not only pixels. A bug can live entirely in metadata.
  4. Control the harness first. Same input twice (randomness), the imported module path (stale install), and known or documented differences.
T4Mutual-information loss (b-spline) binned with the whole batch's min and max. Image A: -1.279 alone, -0.196 batched. Fix: per-sample amin/amax.
T4VQVAE crashed after .half(): the quantizer upcast its inputs but not its codebook. Fixed: bf16/fp16 within 0.45% / 0.06% of fp32, same codes chosen.
T4Lazy crop on a 2D image returned a 3×3 affine. Saved to NIfTI: spacing 1.0, origin 0.0 instead of 2.0, 1.0. Pixels were identical.
art.Rejected: two autoencoders that are random in eval, an fp16 NaN from random-init activations of 1.1e7, and a sweep that imported a stale global install.

Trap: a harness violation is a bug. Half the flags here were randomness, random-init overflow, a stale install or a known issue.

Predict

A masked autoencoder gives a different output for sample 0 when you change sample 1. Before calling it cross-sample leakage, what do you check?

Masked autoencoders draw a random mask on every forward pass, even in eval. If the same input twice already differs, the batch test can't tell leakage from randomness.

Produce

You're handed a new loss and a new segmentation model. Write, in your own words, the checks you'd run. A good answer covers:

  • batch of one versus batched with a very different batchmate
  • whole-model half/bf16 cast against fp32
  • a harness control: same input twice, the import path, known issues
L23 · Workflow · 8 min

Landing work: policy first, shallow clones, red CI

  1. Read the contribution and AI policy before investing effort. It can rule a repo out entirely.
  2. Claims hide in comments and in PRs that cite a different issue number. Search before starting.
  3. Never amend or rebase in a shallow clone. Unshallow first, and after any force-push confirm the PR is still open with a merge base.
  4. On red CI, read which step failed. Setup, upload and label steps aren't your code. Compare the same workflow on main.

Predict

All 21 CI jobs fail in the "Setup Linux" step with git init: Permission denied. Most likely cause?

The failure happens before checkout, so no line of your change has run yet. It's the runner environment.
