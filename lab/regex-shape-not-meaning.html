Regex, Shape Not Meaning

A regex only ever recognizes the SHAPE of text, never what it means. Three lessons from building a teaching tool around that one fact: what regex actually is, a reusable defense that fixes its blind spots, and a lesson about testing your own fix the same way you'd test anyone else's code — because it broke the first time it was run.

L27 · Regex basics · 10 min

A pattern knows shape, never meaning

The entire CDAP bug from a previous lesson lives inside one short pattern. Read slowly, it explains itself.

  1. [...] is a character class — match any ONE character from the set inside the brackets.
  2. + means "one or more" of whatever came right before it.
  3. So [.a-zA-Z0-9_-]+ matches any string built ENTIRELY from: a dot, letters, digits, underscore, hyphen — nothing else.
  4. A string made of nothing but dots — ".." — is built entirely from characters in that set. It matches. The regex has no idea ".." means "go up a directory" in a filesystem; it only ever sees a shape, never a meaning.
pattern[.a-zA-Z0-9_-]+ — the real artifact-name/version check from the CDAP finding.
passes"my-plugin", "1.0.0", and ".." — all three are built only from allowed characters.
combined exampleTensorFlow Serving's real URL matcher: /v1/models/([^/:]+)(?:/versions/(\d+))?:(classify|regress|predict). Four ideas stacked: [^/:]+ is a NEGATED class ("anything except slash or colon"), (\d+) captures digits, (?:...)? makes a whole group optional, (a|b|c) picks exactly one of three words.
anchors matter^[a-zA-Z_][a-zA-Z0-9_]*$ — the ^ and $ pin BOTH ends. Without them, a string like "3x; rm -rf /" can still "match" just because some piece of it looks right.

Trap: treating "it passed the regex" as "it's safe." Those are two different claims. One is about shape. The other is about consequences.

Predict

A regex [.a-zA-Z0-9_-]+ is used to validate a filename before it gets joined into a path. What's the actual gap?

The pattern is doing exactly what it was written to do — checking character shape. The bug is trusting that check to also mean "safe to use as a path segment," which is a completely different, unchecked claim.

L28 · Semantic defense · 12 min

Check the pattern again, after it changes

Two real bugs this session share one root cause: a value gets checked once, then something ELSE transforms it — and nobody checks the transformed version.

  1. TensorFlow Serving's real bug: the URL is checked against a regex BEFORE being percent-decoded. A name like foo%2F..%2F..%2Fbar has no raw slash, so it passes — then decoding turns it into foo/../../bar, which nobody re-checks.
  2. The fix is not a cleverer regex. It's a three-step shape: check the raw value, transform it (decode, resolve, whatever the real code does next), then run the SAME check again on the transformed value.
  3. Add one more piece — containment: does the final, resolved value still live where it's supposed to? A regex can never answer that; only resolving the real path and checking it can.
  4. Double-encoding (encode the payload twice) defeats a guard that only decodes once. The fix: decode repeatedly until the value stops changing, not a fixed number of times — with a safety cap so a crafted input can't loop forever.
guardA small reusable class: require() adds a check, normalize() adds a transform, repeat_until_stable() decodes to a fixpoint.
catchRun for real against foo%252E%252E%252Fsecret (double-encoded ../secret): a guard that decodes once lets it through; the fixpoint version decodes it fully to foo../secret first, then correctly blocks it.
containmentCDAP's fix, in this same shape: resolve the final path, then ask "is this still inside the folder it was supposed to land in?" — Path.relative_to(root) in Python, the same idea in any language.

Predict

A guard checks a value, decodes it once, and stops. What real attack walks straight past it?

Decode-once guards are a very common "quick fix" shape, and double-encoding is exactly the well-known attack built to defeat that specific shape. The honest fix is decoding to a fixpoint, not decoding once and declaring victory.

L29 · Testing your own fix · 10 min

Your own defense needs the same proof anyone else's code needs

Building the general version of the guard above produced a real bug — immediately, the first time it actually ran.

  1. The first version re-ran EVERY check that had already passed, after EVERY later transform, automatically, no exceptions.
  2. That seemed like the more thorough, more "universal" choice. It is also wrong whenever a check was written for one shape of value (a tuple: name and version together) and a later transform changes the value into a different shape (a single resolved path string).
  3. Run against a perfectly valid case, the auto-recheck replayed the tuple-shaped check against a plain string. Indexing a string like a tuple does something that looks like code running — and quietly returns the wrong answer instead of raising an error.
  4. A completely valid, safe input got incorrectly blocked. Found by running the thing, not by reading the code and trusting it.
  5. The real fix: re-checking is something each check opts into by name, not something that happens automatically to everything. "More automatic" is not the same thing as "more correct."
input("my-plugin", "1.0.0") — a completely ordinary, valid artifact name and version.
expectedAccepted.
actual, first versionIncorrectly BLOCKED. The regex check (written for a tuple) got silently replayed against the resolved path string after the path-resolve step.
fixAdded an explicit recheck=True flag per check. Only checks that are genuinely still valid against a later, transformed value get replayed — nothing replays by default.

Trap: assuming your OWN new tool is correct because you understand the intent behind it. Intent is not proof. Running it against real cases — including the boring, obviously-fine ones — is.

Predict

You write a "more thorough" version of a safety check that automatically re-applies every earlier check after every later step. What should you do before trusting it?

A stricter-looking check can still be wrong in a new way — here, a type mismatch that silently returned a bogus answer instead of erroring. Only running it against a real valid case caught that; re-reading the same code a second time would not have.

Produce

Think of a validation or safety check you've written (a form validator, an input sanitizer, anything with an "accept/reject" answer). Write down one completely ordinary, valid input you have NOT actually run through it. Run it. If it's rejected, you've just found the same class of bug as this lesson, for free.
